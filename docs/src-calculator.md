# `src/calculator` — Formulas and processing

This folder holds the **core math and processing**: stats, buffs, damage formulas, attacks, and the optimizer. No Vue or DOM here—pure logic so it can run on the main thread or inside web workers.

## Files

| File | Purpose |
|------|--------|
| **`stats.ts`** | Base stat init, adding buffs (e.g. echo, team), computing self buffs, resonance chain buffs, “additional base” and crit overflow. Exposes `getInitStats`, `addBuffs`, `addEchoBuffs`, `calcCharStats`, and helpers like `getElementDmgBonusByType`, `getDamageValByAttr`. `calculateAllStats` (resolve everything from raw buff config) is a thin wrapper around `calculateFinalStatsFromBuffs` (same pipeline, given already-resolved `selfBuffsData`/`resonanceChainsBuffsData` instead of deriving them) — split so `optimizer.ts`'s per-loadout scoring can compute those once per run/override instead of re-deriving them on every loadout. |
| **`calculator.ts`** | Damage/heal/shield and special formulas: `calcDamage`, `calcHeal`, `calcShield`, `getSpectroFrazzleDamage`, `getAeroErosionDamage`, `calcMidnightVeilDMG`, `calcFixedDamage`, `calcTuneBreak`, etc. |
| **`attacks.ts`** | Attack processing and damage aggregation: `processAttacks`, `calcDamages`, `getCalculationContext`, `aggregateRotationDamage` (sums a resolved attack list into one rotation-level `DamageAggregation`-shaped total — extracted out of `calcDamages` so `optimizer.ts`'s per-loadout scoring can reuse it instead of re-deriving the same reducer). Builds the context (stats, buffs, enemy, rotations) and runs the damage pipeline. |
| **`optimizer.ts`** | Optimizer context and types (`OptimizerContext`), plus the per-loadout scoring helpers shared by the main-thread `optimize()` and `processor.worker.ts`'s `processLoadout` (previously two independently-copy-pasted, drifted implementations): `computeLoadoutFinalStats` (combines a loadout's echo/set-bonus/main-echo stats and runs `calculateFinalStatsFromBuffs`), `buildOptimizerCalculationContext` (the one call site for `getCalculationContext`'s 50+ positional args — takes an optional 4th `overrideBuffData` arg so an override action's own resolved self/resonance/team-buff data reaches `getCalculationContext` instead of the character's un-overridden defaults; `getCalculationContext`/`processAttacks` re-derive some bonuses straight from these raw objects, not just from the already-flattened `finalStats` numbers, so passing the wrong ones here silently reintroduces or drops buffs even when `finalStats` itself was computed correctly), `computeOverrideBuffVariants`/`scoreOptimizerRotation` (full per-action `advancedConfig` support for the `Rotation:<id>` target — see below). `computeOverrideBuffVariants`'s team-buff resolution includes the two selected teammates' buffs *and* the echo-granted/weapon-granted team buff pools (`allEchoBuffs`/`allWeaponTeamBuffs`) every character has access to regardless of team selection — omitting the latter two (issue #401 follow-up) silently dropped any enabled echo/weapon team buff for an override action. Heavy combo generation and evaluation run in workers that use this context. |
| **`rotationData.ts`** | `buildOptimizerRotationData(rotation, chosenChar, characterLevel)` — resolves a rotation's actions once per optimizer run into `plainAttacks` (no `advancedConfig`, share one batched context) and `overrideActions` (a real per-buff override, each carrying its own `advancedConfig`), mirroring `characterRotation.ts`'s plain/override split. Feeds `optimizer.ts`'s `computeOverrideBuffVariants`/`scoreOptimizerRotation`: `computeOverrideBuffVariants` (once per run) merges each override action's `advancedConfig` onto the character's stored build via `applyAdvancedOverrides` and re-resolves self buffs/resonance chains/team buffs/weapon passives against it; `scoreOptimizerRotation` (per loadout) scores `plainAttacks` via the existing shared-context path and each override action via its own rebuilt `finalStats` (re-resolving echo-set-passive stats per loadout, since which set bonus applies depends on the loadout under test), merging results back into the rotation's original order. The one category left unsupported is a per-action main-echo-buff override — the Optimizer's fast-path `mainEchoStats` lookup isn't override-aware — surfaced to users via a warning in `CalculatorOptimizer.vue` rather than silently ignored. |
| **`resolveRotationAction.ts`** | `resolveRotationActionToAttackData` — maps one persisted `RotationAction` (character + skill key + count + buffs/overrides) to a full attack-ready object for `processAttacks`. Used by both the single-character rotation system and Team Rotations. |
| **`buildCharacterContext.ts`** | `buildCharacterCalculationContext(characterId, characters, enemyConfig, inventoryEchoes?, options?)` — headless (no Vue/"active character" dependency) reconstruction of a character's full calculation context directly from stored build data: weapon (incl. passives), echoes (incl. set bonuses + main echo buff), self buffs, resonance chains, team buffs, and `calculateAllStats`/`getCalculationContext` output. Also returns a `definitions` catalog (raw buff/passive/resonance-chain *definitions*, not just their computed values) consumed by Team Rotations' Advanced-mode per-action buff editor. `options.alwaysEnabledOnly` resolves only permanently-active contributions — base stats plus weapon passives/echo set bonuses/main-echo buff whose definitions carry `alwaysEnabled: true` — dropping character self-buffs, resonance chains, team buffs, and custom buffs entirely regardless of their stored toggle state; used by `CalculatorBuildCard.vue` to represent equipment alone (issue #383). See ADR [0011](./adr/0011-headless-character-calculation-context.md). |
| **`rotationAdvancedBuffs.ts`** | Shared per-buff override machinery used by both Team Rotations and Character Rotations. `RotationAdvancedConfig`/`RotationBuffOverride` — a per-action override (`{isEnabled?, stacks?, baseAttrValue?}`) for each buff category (self buffs, weapon passives, echo set passives, main echo buff, team buffs, resonance chains). `applyAdvancedOverrides(characterData, overrides)` — clones a character's stored build data with the overrides merged in (keys not present in `overrides` fall through to the character's real stored config), so the existing `buildCharacterContext.ts` pipeline can be reused as-is for a single action instead of the whole character. `buildAdvancedConfigSnapshot(characterData, definitions, "current" \| "blank")` — builds a full `advancedConfig` up front, either mirroring the character's real current buff state (so the advanced buff panel's checkboxes aren't misleadingly blank) or fully disabled. `applyBulkAdvancedConfigOverride(actions, actionIds, category, key, override)` — stamps one concrete override into every listed action's `advancedConfig`; the mechanism behind the per-buff "Duration" control. `hasAdvancedConfigOverrides(config)` — true when a config actually overrides something, vs. an empty/never-touched one; used to decide whether an action needs its own rebuilt context or can share a batched one. `mainEchoBuffOverrideDiffersFromCharacter(mainEchoBuff, characterData)` — true only when a persisted `mainEchoBuff` override's *value* actually diverges from the character's own current main-echo config, not just whether the key is present; the buff panel's "current"-mode snapshot means `advancedConfig.mainEchoBuff` is set on nearly every customized action even when unchanged, so `hasAdvancedConfigOverrides`-style presence checks over-fire for anything gated specifically on a real main-echo-buff divergence (used by `CalculatorOptimizer.vue`'s override warning, see below). |
| **`teamRotation.ts`** | `calcTeamRotationDamage` — evaluates a rotation spanning up to 3 characters by delegating each slot's actions to `characterRotation.ts`'s `calcCharacterRotationDamage` (no team-wide "mode" — every action is scored per its own `advancedConfig` automatically), passing `team.buildIds?.[slot] ?? null` through as that call's `buildId` (issue #278 — a slot can pin a specific build without changing which build is active for that character elsewhere), then sums the per-slot results into per-character/team totals. `convertRotationActionsForSlot(sourceActions, slot, startOrder)` — converts a single-character rotation's actions (from `characters[id].rotations` or a character preset) into team actions pinned to one slot, regenerating ids and continuing the order sequence, carrying each source action's `advancedConfig` through unchanged; used when importing a rotation into a team slot. `calcRotationDps` — shared DPS-from-duration math, used by both Team Rotations and `CalculatorDamages.vue`. `DamageAggregation`/`addDamageAggregation` are re-exported from `characterRotation.ts`, which owns them (see that entry) to avoid a circular import. |
| **`characterRotation.ts`** | `calcCharacterRotationDamage(rotation, baseContext, characterId, characters, enemyConfig, inventoryEchoes, buildId?)` — the shared engine behind both the single-character Character Rotation display and `teamRotation.ts`'s per-slot scoring (no Basic/Advanced mode toggle anywhere in the app anymore): actions with no `advancedConfig` share `baseContext` (a single batched `calcDamages` call) via one batched call; actions that do have a real override (`hasAdvancedConfigOverrides`) each get their own freshly-rebuilt context via `buildCharacterContext.ts`. Results from both paths are merged back into the rotation's original action order. `baseContext` is optional — pass a caller-supplied one to reuse it (Calculator.vue passes its own live, reactively-maintained context, so the common no-override case pays no extra cost), or `null` to have this function build one itself (what `calcTeamRotationDamage` does per slot, since it has no single "active character" context to reuse). `buildId` (issue #278, Team Rotations' per-slot build override) swaps a specific saved build's data in for `characterId` via `resolveCharactersForBuild` (`buildOverride.ts`) before either path runs, so a per-action `advancedConfig` override composes on top of the *targeted build's* data rather than the active build's; don't combine a non-null `baseContext` with `buildId` (see the function's own doc comment) — `calcTeamRotationDamage` never does. Also owns `DamageAggregation`/`addDamageAggregation`/`EMPTY_DAMAGE_AGGREGATION` (re-exported from `teamRotation.ts` for existing consumers). Replaced the old per-attack `excludeTeamBuffs`/`excludeWeaponBuffs` category-exclude flags (see issue #401) — nothing in the app writes those legacy flags anymore (Team Rotations' old mode toggle was the last consumer); `attacks.ts`'s branches that still read them are fully dead code, left in place pending a separate cleanup pass. |
| **`buildOverride.ts`** | `resolveCharactersForBuild(characters, characterId, buildId)` — returns a `characters` map with `characters[characterId]` replaced by a specific saved build's data (`characters[characterId].builds[]`, see `src/characters/buildFields.ts`), falling back to the map unchanged when `buildId` is null/undefined or doesn't match any stored build (deleted build, or a team imported into a different profile — never a hard error). Mirrors `rotationAdvancedBuffs.ts`'s `applyAdvancedOverrides` synthetic-characters-map trick so `buildCharacterCalculationContext` itself never needs to know about builds. Used by `characterRotation.ts`'s `calcCharacterRotationDamage` for its `buildId` param. |

## Data flow (conceptual)

1. **Stats**  
   Base stats (from character + level + weapon) → add echo stats → apply self buffs → resonance chain buffs → additional base/crit overflow → **final stats**.

2. **Damage**  
   Final stats + enemy + rotation/attack list → `getCalculationContext` → `calcDamages` (which uses `calculator.ts` and `processAttacks`).

3. **Optimizer**  
   Main thread builds `OptimizerContext` and sends batches to `processor.worker.ts`; workers use `stats.ts` and damage logic to evaluate loadouts and return results.

## Important conventions

- **No Vue / DOM**: Only TS and data. This keeps the logic worker-safe and testable.
- **Serializable context**: Optimizer and any worker entry points receive plain objects (no functions) so they can be postMessage’d.
- **Performance**: These functions run on every relevant user change; keep hot paths tight and data structures efficient.

## Type definitions

Types are defined in the same files or in `optimizer.ts` for optimizer-specific shapes. As the codebase is typed further, key interfaces (e.g. stat object, calculation context) should live here or in a small shared types module used by both `calculator/` and `workers/`.
