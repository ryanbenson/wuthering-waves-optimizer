# `src/stores` — Pinia stores (user data only)

Pinia stores hold **user input and user state only**. They are the only place that should persist the user’s choices (character, weapon, echoes, buffs, rotations, etc.). Config, feature flags, and constants belong in code, not in stores.

## Principles

1. **User data only**  
   Stores hold what the user selected or entered: active character, per-character weapon/echoes/buffs/rotations/optimizer settings, inventory echoes, presets, and app-level preferences that are clearly “user settings” (e.g. theme). No app config or env.

2. **Auto-sync to storage**  
   Stores are persisted (e.g. to localStorage) so the user’s setup survives reloads. The persistence layer is configured at app init (e.g. via a Pinia plugin). Do not put non-user data in the same persisted state.

3. **Patch-friendly**  
   If a bug or misconfiguration is in code (e.g. wrong default or validation), we want to fix it with a code patch without migrating or editing the user’s saved data. Therefore:
   - Avoid storing derived or redundant config that could go stale.
   - When reading, tolerate missing or legacy keys (default in code) rather than assuming a specific stored shape forever.

## Stores

| Store | File | Purpose |
|-------|------|--------|
| **character** | `character.js` | **`characters`**: object keyed by character id; each value holds that character’s stored data (weapon, echoes, buffs, resonance chains, rotations, talents, characterLevel, enemy settings, optimizer min stats, `customPortrait`, etc.). `customPortrait` (added for the Build Card screen, `CalculatorBuildCard.vue`) is an optional base64 JPEG data URL — set via `CalculatorBuildCardPortraitUpload.vue`, which resizes/re-encodes the uploaded image client-side (`src/utils/imageCompression.ts`, capped at 800px/quality 0.8) before persisting, since it's stored as-is in localStorage; `null`/absent falls back to the character's default CDN portrait. Purely additive — no migration needed, `hardSetState`/export-import round-trip it unchanged like every other field. **Multiple builds** (issue #278): each character record also holds **`builds`** (array of `{id, name, createdAt, updatedAt, ...every field on the record except `characterLevel`/`talents`}` — see `src/characters/buildFields.ts`'s `extractBuildFields`/`applyBuildFields`/`omitBuildMetadata`, a denylist rather than an allowlist so new fields are automatically build-scoped) and **`activeBuildId`**. The top-level fields (`weapon`, `echoes`, `buffs`, etc.) always mean "the active build's live data" — nothing that reads them needs to be build-aware; only switching is new. Note the deliberate naming collision with the pre-existing, unrelated `buildStatus`/`buildComplete` (character setup-completion status, now itself build-scoped) and the "Build Card" export feature — both predate this feature and use "build" for a different concept. Actions: `ensureCharacterBuilds` (idempotent — synthesizes a "Default build" if missing), `createBuild(characterId, name, { from: "active" \| "blank" })`, `renameBuild`, `deleteBuild` (refuses to delete a character's only build), `equipBuild` (commits live fields back into the outgoing build, then copies the target build's fields onto the live record and syncs the `inventory` store's `equipped`/`equippedPresets` maps to match — UI bookkeeping only, since `buildCharacterContext.ts` resolves echo stats by `echoId` lookup directly and never consults `equipped`). Getters: `getBuilds`, `getActiveBuildId`, `getActiveBuild`. `characters[id].substatWeights` (issue #451, optional) is that character's substat priority overrides for the Substat Score — resolved via getter **`getCharacterSubstatWeights(characterId)`** (curated default from `src/characters/substatPriorities.ts`, if any, layered under any user override, both layered under the neutral default), set/cleared via **`setCharacterSubstatWeights`**/**`resetCharacterSubstatWeights`**. Unlike most character fields it's in `SHARED_FIELD_KEYS` (`src/characters/buildFields.ts`), not build-scoped — it's a preference about the character, not the equipped loadout. No migration needed (absent-safe, same as `optimizer.minStats`). **`activeCharacter`**: current character id. Actions: `setActiveCharacter`, `setCharacterData`, `setCharacterEchoes`, `setCharacterRotations`, `setCharacterOptimizerMinStats`, `hardSetState`, etc. |
| **inventory** | `inventory.js` | **`echoes`**: user’s echo inventory. **`equipped`**: which echoes are equipped to which character/slot. **`echoPresets`**, **`equippedPresets`**: preset loadouts and which character uses which preset. Getters: `duplicateEchoIds`, `getEquippedEchoData`, `echoById`, etc. |
| **settings** | `settings.js` | App-level user preferences (e.g. theme, UI toggles). Only user-facing settings; no internal config. `config.echoRatingWeights` (issue #451, optional) is the global substat priority profile for the always-visible Echo Rating — getter **`echoRatingWeights`** resolves it against the neutral default; **`setEchoRatingWeights`**/**`resetEchoRatingWeights`** write/clear it. |
| **teamRotations** | `teamRotations.js` | **`teams`**: array of `{id, name, characterIds: [3], buildIds: [3], actions: [{id, slot, order, ...same fields as a single-character RotationAction, advancedConfig?}], duration, enemyConfig, mode: "basic" \| "advanced"}`. `mode` gates whether an action's `advancedConfig` (per-buff-category overrides — self buffs, weapon passives, echo set passives, main echo buff, team buffs, resonance chains) is applied; `advancedConfig` is otherwise ignored. `buildIds[slot]` (issue #278) optionally pins that slot's calculation to one of that slot's character's saved `builds[]` entries instead of whichever is currently active — `null`/absent (including on teams saved before this field existed) means "use the active build"; `setTeamCharacter` resets a slot's `buildIds` entry to `null` whenever that slot's character changes, the same way it already clears the slot's `actions` (see `calculator/teamRotation.ts`/`buildOverride.ts`). Each team references character ids from the `character` store's `characters` map — it does not duplicate build data (export/import preserves this: only the team's own config round-trips, never the referenced characters' builds). Actions: `createTeam`, `importTeam` (builds a team from parsed export/preset data with a fresh id), `renameTeam`, `deleteTeam`, `setTeamCharacter`, `setTeamCharacterBuild`, `setTeamDuration`, `setTeamActions`, `setTeamEnemyConfig`, `setTeamMode`, `hardSetState`. |

## Usage from components

- **Calculator** and others use `useCharacterStore()` and `useInventoryStore()` with `storeToRefs()` so the UI reacts to store changes. They call actions to update after user actions (e.g. `setCharacterData`, `setCharacterEchoes`).
- **No config in store**: Things like “list of characters,” “echo stat tables,” or “damage formula constants” are read from `src/characters`, `src/echoes`, `src/calculator`, etc., not from store state. The store only remembers the user’s choices so they can be restored after reload.
