# 12. Echo & character substat ratings

## Context

Issue [#451](https://github.com/ryanbenson/wuthering-waves-optimizer/issues/451) asked for a per-echo quality grade (E-SSS, based on how well its substats rolled), a way for users to customize which substats they value, and a second, character-specific "Substat Score" (0-100%) that scores an echo against one particular character's stat priorities.

The codebase already had a closely related, un-surfaced building block: `src/echoes/stats.ts`'s Roll Value (RV) / Crit Value (CV), which sum a per-substat roll-quality lookup table into a single number. This feature extends that pattern (same 8-tier roll lookup, reinterpreted as 1-8 points) rather than inventing a new one.

## Decision

1. **Two distinct scores**, both sharing an 8-letter grade vocabulary (E/D/C/B/A/S/SS/SSS) and color scheme (white/green/blue/purple/purple/gold/gold/red):
   - **Echo Rating** — global, always-visible, computed from raw substat roll tiers (1-8 pts × 5 substats = 5-40 pt range) weighted by one global, user-customizable priority profile. Default weight is uniform (`1` per stat), which reproduces the plain 5-40 point range with no bias.
   - **Substat Score** — per-character, 0-100%, `Σ(rollTier × characterWeight)` over the echo's revealed substats, divided by that character's *ideal* 5-substat echo ceiling (see the bug-fix update below for why the denominator isn't just the echo's own substats).

   Grade bands for Echo Rating are fixed integer point ranges (E 5-12 … SSS 27-40); Substat Score bands are equal-width percentages (E 0-12.5% … SSS 87.5-100%) since a normalized percentage doesn't share the point scale's natural anchors. When a weight profile is non-uniform, the weighted point sum is normalized back onto the 5-40 scale so the same Echo Rating bands stay meaningful.

   Both are "provisional" (asterisked) whenever an echo has fewer than 5 revealed substats — there's no per-roll history stored, so "5 rolls" is read as "all 5 substat slots revealed" (reusing the existing `isEchoIncomplete` signal).

   **Update (post-launch user feedback):** wherever an echo is being evaluated in a specific character's context (equipped slot, Build Card, optimizer results, the echo picker opened from a character's Echoes tab), only the Substat Score badge is shown — not the generic Echo Rating badge too. Showing both was confusing (an echo can be a global SSS on raw roll quality while being a poor fit for the specific character looking at it, e.g. missing that character's highest-weighted stat entirely). The generic Echo Rating stays the only badge in character-agnostic contexts (inventory, general echo browsing), and it now also carries a percent (`(points - 5) / 35 × 100`), not just the letter, to match. `CalculatorEchoCard.vue` picks between them via `v-if="substatScore"` / `v-else`; components that are *always* character-scoped (`CalculatorEcho.vue`, `CalculatorOptimizerResultLoadoutEcho.vue`, `CalculatorBuildCardEchoCard.vue`) render the Substat Score unconditionally and never compute the generic grade at all. The Substat Score badge now also carries its own letter grade (e.g. "A 51%"), not just the percentage, so rollups (Calculator header, character browser cards, `CalculatorCharacterCard.vue`, and the new one on `CalculatorBuildCard.vue`) can all show a grade too.

   **Update (bug fix #1, post-launch user feedback):** the Substat Score's denominator was wrong. It summed `8 × weight` only over the substats the specific echo actually has, which meant a substat the character's profile weights highly but that's simply *absent* from the echo contributed to neither the numerator nor the denominator — effectively excluded from the ratio instead of correctly dragging the score down. A real example caught this: an echo for Aemeath (`{ CritRate: 4, CritDMG: 4, ATK: 2, ResonanceLiberationDMGBonus: 1.5, ATK_FLAT: 1 }`) with no Crit Rate substat at all — her single highest-weighted stat — scored "A 51%" under the old formula; a reference site running the same rating design scored the identical echo "C 32.1%". Fixed by making the denominator a *fixed* per-character ceiling — `getBestPossibleWeightedTotal`: independent of what any particular echo happens to roll, so a missing priority stat is scored as a genuine loss.

   **Update (investigated against the reference implementation's actual source, then deliberately diverged from it):** the user offered the reference's repo directly ([DJ12421/Tacet-Lab](https://github.com/DJ12421/Tacet-Lab) — the same project bug fix #1's weight data was sourced from), which let fix #1 be checked against their real algorithm instead of guessed at. Fetched via the GitHub API's git-tree endpoint (code search requires auth) and cross-referenced `src/domain/character-substat-score.ts`, `src/domain/echo-roll-tier.ts`, and `src/game-data/tunable-rolls.ts`. Two findings: (a) their roll-value tables match ours exactly, position-for-position, ruling out a data-table mismatch; (b) they treat the 3 flat substats (raw HP/ATK/DEF — `HP_FLAT`/`ATK_FLAT`/`DEF_FLAT` here) specially: instead of a real tier lookup, a flat substat is *always* worth a constant `3` points (their `FLAT_STAT_POINTS`) regardless of roll, and in the ideal-echo ceiling only the character's *single* highest-weighted flat stat counts (at ×3, not ×8), kept separate from a top-5-non-flat pool. Replicating this exactly reproduced their number precisely: the Aemeath echo landed at 30.5/95 = **32.105%**, matching their site's 32.1% to 3 significant figures — confirming the discrepancy really was this one mechanism, not a data or rounding difference.

   Having confirmed *why* the numbers differed, the constant-`3` choice itself was then scrutinized rather than adopted on authority: it isn't derived from expected-value math on either roll table (the probability-weighted average tier is ~2.35 for ATK_FLAT/DEF_FLAT, not 3), and — more importantly — `HP_FLAT` actually has the *same* 8-value roll table and probability distribution as any %-based substat (verified directly against their own `tunable-rolls.ts`: `hp`'s probabilities are byte-for-byte identical to their shared `commonPercent` table); only `ATK_FLAT`/`DEF_FLAT` are genuinely coarser (4 values). Grouping all three under one constant discards real signal `HP_FLAT` actually carries. Given this project's stated accuracy-first priority (`CLAUDE.md`), the user chose to diverge from the reference here: substats are scored purely from their own real tier count (`getSubstatTierCount`, derived from `subStatsTable[stat].length` — 8 for most stats and `HP_FLAT`, 4 for `ATK_FLAT`/`DEF_FLAT`) with no flat/non-flat special-casing anywhere. `getBestPossibleWeightedTotal`'s ceiling picks the top 5 stats by `weight × ownTierCount` (not weight alone), so a low-granularity stat like `ATK_FLAT` is correctly valued below an equally-weighted 8-tier stat without an arbitrary constant. This also incidentally resolves an artifact of the reference's model: because their ceiling credits a non-flat top-5 *and* a separate flat slot (6 "slots" worth, when a real echo only has 5), even a perfect roll couldn't reach 100% under any profile weighting a flat stat — under this implementation a perfect 5-substat echo is exactly 100% again, as originally designed. The Aemeath echo now scores 30.5/96 = **31.77%** ("C" — one band down from the reference's, by design) — see the boundary tests in `tests/echoes/rating.test.ts` and `tests/composables/useEchoRating.test.ts` for the full worked numbers, kept intentionally in the test comments as a record of *why* this project's numbers won't always match that reference's.

   RV was also hidden from all badges/filters in the same pass (`SHOW_ROLL_VALUE_BADGE` in `src/echoes/stats.ts`, a single toggle — now redundant with Echo Rating/Substat Score, data/computation untouched in case it's wanted back). "Build Score" is the rollup-specific label (Calculator header, character browser cards, `CalculatorCharacterCard.vue`, and a new top-right badge on the identity panel of `CalculatorBuildCard.vue`) — distinct from the per-echo "Substat Score" badge, since a rollup answers "how good is this whole build" rather than "how good is this one echo." No store/schema change from any of this.

2. **New pure module `src/echoes/rating.ts`**, not folded into the already-large `stats.ts`. Substat weight profiles are plain `Record<string, number>` objects on the same 13-key `subStats` vocabulary `stats.ts` already defines; `resolveSubstatWeights(baseline, ...sources)` layers a caller-chosen baseline under curated-then-user-override sources.

   **Update (post-launch user feedback):** the baseline differs by context. `DEFAULT_SUBSTAT_WEIGHTS` (neutral, every stat weighted `1`) is used for the global Echo Rating and for any character with *no* curated profile — there's no basis to assume one stat matters less than another yet. `ZERO_SUBSTAT_WEIGHTS` (every stat weighted `0`) is used as a *curated* character's baseline: a curated profile is a deliberate, complete statement of what matters for that character (sourced from Tacet Lab's DPR-calc data), so a stat it doesn't mention should count for nothing toward that character's Substat Score, not the neutral default. `character.js`'s `getCharacterSubstatWeights` picks the baseline per-character based on whether `getCuratedSubstatWeights` returns anything.

3. **Curated per-character defaults sourced from an external reference**, not hand-guessed. [Tacet Lab](https://github.com/DJ12421/Tacet-Lab/blob/main/src/game-data/character-substat-preferences.ts) (GPL-3.0 — same license as this project, so no compatibility issue) publishes a DPR-calc-derived substat priority dataset on the same 0-4/0.5-step scale for ~50 characters. `src/characters/substatPriorities.ts` is a single static `Record<characterFolderKey, SubstatWeights>` lookup transformed from that dataset (their 13 stat keys and character display names remapped onto this repo's `subStats` keys and `src/characters/<Key>` folder names; their single "Rover: `<Element>`" entries applied to both this repo's male/female folders per element). A first hand-guessed draft used "Healing Bonus" as a healer substat weight — a real bug, since Healing Bonus is an echo *main* stat only and can never be a rolled substat; `tests/characters/substatPriorities.test.ts` guards against this class of mistake by asserting every curated key is a real substat.

   This is a single lookup file, not per-character `substatPriorities.ts` files wired into each character's `getData()` — the data is tiny (a handful of numbers per character) and a single synchronous file avoids forcing every lookup through the async `getCharByName` dynamic-import path that the heavier per-character kit data (attacks, buffs) needs for code-splitting.

   Characters the source itself left blank (mostly healers/shielders without a usable DPR-calc graph) and characters added to this repo since the source's last sync (Jingran, Qingxiao) are omitted rather than guessed — they fall back to the neutral default profile, fully user-customizable per character via `EchoRatingWeightsEditor.vue`.

4. **No migration for the new store fields.** `settings.js`'s `config.echoRatingWeights` and `character.js`'s `characters[id].substatWeights` are both optional and absent-safe (missing → falls back to defaults at read time, via `resolveSubstatWeights`/`getCharacterSubstatWeights`). `characters[id].optimizer.minStats` — a directly analogous purely-additive optional field on the same character record — never received its own migration; only `builds` (migration 008) did, because it needed to *synthesize* a "Default build" from existing fields. Since neither new field requires restructuring existing data, they follow `minStats`'s precedent rather than getting a version bump.

   `substatWeights` **was** added to `SHARED_FIELD_KEYS` in `src/characters/buildFields.ts` — it's a character-level preference like `characterLevel`/`talents`, not a per-build field, so it must not be silently reset when switching builds.

5. **UI weight editor uses `Range.vue` (tick slider), not a numeric input.** Since a weight can only be one of 9 discrete values (0, 0.5, 1, …, 4), a tick slider communicates the constraint better than a free numeric field — and `Range.vue` was already used exactly this way for substat *value* entry in `CalculatorEcho.vue`.

6. **The Echo Rating filter range is shared across both echo browsers** (`InventoryEchoesBrowser.vue`, `CalculatorEchoesBrowser.vue`) via a new `EchoRatingRangeFilters.vue`, modeled directly on the existing `EchoCvRvRangeFilters.vue`. Neither browser has a general sort feature (checked during implementation — only CV/RV range filters exist today), so "add Rating to sort" from the original issue language was dropped rather than invented from scratch.

## Consequences

- Pros: reuses the existing RV/CV roll-quality data table instead of a parallel one; curated per-character weights for ~50 of 62 characters are sourced from published DPR-calc math rather than guessed, with the guess-vs-source distinction caught by a real bug during implementation; no schema migration needed; the weight-editor UI matches an existing input pattern instead of introducing a new one.
- Cons: 12 characters (mostly supports) have no curated default and fall back to neutral weights until either the source project publishes one or a user customizes it themselves; the single `substatPriorities.ts` lookup file will need manual updates if new characters are added faster than the upstream source syncs.

## Guidance

- **Do** extend `src/characters/substatPriorities.ts` (not per-character files) if adding more curated defaults — keep it a single synchronous lookup.
- **Do** add a test asserting any new curated weight key is a real member of `subStats` (see `tests/characters/substatPriorities.test.ts`) — "Healing Bonus" is a recurring trap since it's a valid *main* stat but not a substat.
- **Don't** add a migration for future optional, absent-safe fields on `characters[id]` unless existing data needs restructuring — follow the `minStats` precedent, not `builds`.
- **Don't** forget `SHARED_FIELD_KEYS` in `buildFields.ts` when adding another character-level (not build-level) preference field.
