# `src/components` — Vue components and data flow

All Vue components that power the app live here. The **Calculator** is the main orchestrator: it owns the calculation state, wires stores and character/echo/weapon data, and drives stats and damage updates.

## Calculator.vue — main orchestrator

**Location**: `src/components/Calculator.vue`

### Role

- **Single source of “current calculation” state**: character, weapon, echoes, team buffs, resonance chains, talents, enemy, custom buffs, rotations, optimizer results, and all derived stats and damages.
- **Orchestrates the pipeline**: When the user changes anything (character, level, weapon, echoes, buffs, talents, enemy, rotations), Calculator either:
  - Updates reactive state from the store or child events, then
  - Calls **`computeAllBuffsWithBreakdown()`** (which uses `calculateAllStats` from `calculator/stats.ts`) to get final stats and buff breakdowns, then
  - **`updateStats(finalStats)`** to push stats into refs, then
  - **`calcAllDamages()`** (async) to build the calculation context and run `calcDamages` from `calculator/attacks.ts`, storing the result in `allDamages`, then computes each rotation's own damage via `calcCharacterRotationDamage` (`calculator/characterRotation.ts`) — decoupled from `calcDamages`' own (now-unused-for-rotations) `rotationsList` branch, since actions with a per-action `advancedConfig` override need their own freshly-rebuilt context, while plain actions reuse the context just built above (no extra cost for the common case) — and assigns the results to `allDamages.rotations`.
- **Passes data down**: Child components receive props (e.g. `character`, `totalAtk`, `allDamages`, `charBuffsData`, `teamBuffsData`, `rotationsList`) and emit events (e.g. `@update-weapon`, `@updated-team-buffs`, `@updated-rotations`). Calculator handles those events and re-runs the pipeline.

### Data flow (summary)

1. **Stores**  
   `useCharacterStore()` and `useInventoryStore()` (Pinia). Calculator uses `storeToRefs` for `characters`, `activeCharacter`, and reads/writes character data (weapon, echoes, buffs, rotations, optimizer settings, etc.). Inventory store is used for echo inventory and presets.

2. **Character selection**  
   When `character` (ref) changes, a `watch`:
   - Fetches full character data with `getCharByName(charName)`.
   - Sets `chosenChar`, weapon type, base stats, enemy defaults, and character element.
   - Calls `computeAllBuffsWithBreakdown()` → `updateStats()` → `calcAllDamages()`.

3. **Weapon / echoes / buffs / talents / enemy / rotations**  
   Handlers (e.g. `handleWeaponUpdated`, `updateStatsEchoes`, `handleUpdatedTeamBuffs`, `handleCharacterTalentUpdated`, `handleUpdatedEnemy`, `handleUpdatedRotations`) update the relevant refs/reactive objects, then call the same pipeline: `computeAllBuffsWithBreakdown()` → `updateStats()` → `calcAllDamages()` (and for rotations, also rebuild rotation list from store/talent data).

4. **Optimizer**  
   Optimizer runs in a web worker. Calculator passes context (stats, combos, target type, etc.) and receives results via `handleOptimize`; it then updates `optimizerResults` and related refs for the optimizer UI.

5. **Output**  
   **CalculatorStats** and **CalculatorDamages** receive the computed stats and `allDamages` and display them. **CalculatorBreakdown** (teleported to sidebar) shows detailed breakdown for a selected stat or attack.

Character name and weapon name are colored by rarity (amber/violet) with a star row underneath, matching convention. The toolbar also holds card-branding fields — in-game username, optional UID, and a full-card background image — stored in `useSettingsStore`'s `config.buildCard` (not per-character, since this is the player's identity across every build they export) and rendered as a `background-image` on `.build-card__canvas`. Unlike every other screen, this one hides the always-on `.results` side panel and collapses `.calculations` to a single column via a `calculations--full-width` class bound to `curScreen === 'build-card'` (see `Calculator.vue`'s scoped styles). The card's internal layout always uses the desktop 3-column grid regardless of viewport — it's rendered at a fixed 1920x1080 size and scaled down via CSS `transform` for on-screen preview, so viewport-width breakpoints inside it would be meaningless; on shorter screens the preview scrolls within `.calculations__screens` (an `overflow-y:auto` ancestor, pre-existing/unrelated to this card) rather than shrinking further. Copy/download (`utils/exportCardImage.ts`, via `html-to-image`) temporarily reset that preview `transform: scale(...)` to `1` before capturing and restore it after, since `html-to-image` clones the live node including its inline transform — capturing while shrunk for preview would otherwise bake the shrink into the exported PNG.

Navigation between these screens is controlled by `curScreen` and sub-nav components (`CalculatorSubNav`, `CalculatorMobileSubNav`).

## How components are put together

- **Layout**: `Nav` wraps the calculator and provides desktop/mobile sub-nav; screens are toggled with `v-show="curScreen === '...'"`.
- **Data**: Top-down via props from Calculator; bottom-up via `emit` (e.g. `@update-weapon`, `@updated-team-buffs`). No global event bus; state is either in Pinia (persisted user data) or in Calculator’s refs/reactive (derived and ephemeral).
- **Styling**: DaisyUI + Tailwind. Components use semantic classes so themes (light/dark) work everywhere.

## TeamRotations.vue — multi-character team rotation page

**Location**: `src/components/TeamRotations.vue` (routed at `/teams`, wrapped by `src/pages/TeamRotationsView.vue`)

Unlike Calculator.vue, this page does **not** own a single character's reactive calculation state. Each team references up to 3 already-configured characters by id (from the `character` store's `characters` map) and computes each one's stats/damage independently via `buildCharacterCalculationContext` (`src/calculator/buildCharacterContext.ts`) — see ADR [0011](./adr/0011-headless-character-calculation-context.md).

- **`TeamRotations.vue`** — lists teams from the `teamRotations` store, create/delete, selects one to edit. Also hosts "Import Team" (paste JSON or upload a `.json` file) and "List Presets" (curated teams from `src/teamRotations/presets.ts`) panels, both funneling into `teamRotationsStore.importTeam(...)`. `TeamRotationTeamEditor.vue` has the matching "Copy Team"/"Download Team" export buttons. `src/teamRotations/exportImport.ts` is the pure (de)serialization layer shared by both directions: `buildTeamExportPayload`/`generateTeamExportFilename` for export, `parseTeamImportPayload` for import — the export/import format is only the team's own config (name/characterIds/actions/duration/enemyConfig), matching the store's reference-only design (never the referenced characters' full builds). A stray `mode` field in an old export/import payload is silently ignored (see issue #401 — the Basic/Advanced mode toggle this used to select is gone). `src/teamRotations/presets.ts` is a hand-maintained `TeamRotationPreset[]` (`{name, description, author, data}`, `data` being the exact shape a team export produces) — mirrors the existing per-character `rotations`/`echoes` preset pattern in `characters/<Name>/presets.ts`.
- **`TeamRotationTeamEditor.vue`** — per-team editor: 3 character-picker slots (restricted to configured characters) with a grid/icon stat snippet (HP/DEF/ATK/Crit Rate/Crit DMG/Energy Regen), a "Configure Character" button that sets that character active and navigates to `/` (configuring a build always happens on the Calculator page, never here), and an "Import Rotation" button (see `TeamRotationImportRotation.vue` below); shared enemy config; team name + rotation duration; the actions list; and a single slideout drawer holding both the damages list and (when a row is clicked) the attack breakdown, as two views of one panel. The drawer is a *separate* `.drawer`/`.drawer-side` from the rest of the page content (not nested inside `.drawer-content` — `.drawer-side` is `position:fixed` and doesn't participate in the drawer's own grid track sizing, so nesting real content there mis-sizes the "max-content" column and pushes the panel off-screen), with an explicit ✕ close button plus its usual click-outside-to-close overlay. Its `z-[60]` (above the app's fixed nav at z-50) is applied directly on `.drawer-side` — NOT the outer `.drawer` wrapper, which has no `position` set and so gives a z-index class no stacking effect at all; that bug had left the drawer at its default stacking level, letting the nav visually bleed through its edge and letting other positioned page content (like the sticky summary header) sit above the drawer-overlay and swallow "click outside to close" clicks. Also locks `document.body`'s scroll while open (restoring whatever value was set before, e.g. by `AppLayout.vue`'s own route-based toggle) since the drawer's content lives outside `.drawer-content` and so doesn't get daisyUI's usual "underlying page can't scroll" behavior for free — without the lock, the page behind kept scrolling too, showing two scrollbars at once. `addAction()` no longer stamps a fresh action with an `advancedConfig` snapshot — it starts with none, exactly like `CalculatorRotation.vue`'s own `addAction`, since `TeamRotationActionEditor.vue`'s buff panel now shows the character's real current state as a display-only fallback (see that entry). `handleImportRotation` no longer overwrites an imported action's `advancedConfig` either (issue #401 fix — it used to replace whatever per-action customization the source Character Rotation had with one uniform "current state" snapshot for every imported action, silently discarding the actual customization; `convertRotationActionsForSlot` already carries it through correctly on its own). Rebuilds each slot's calculation context and the team's damage/DPS fresh on every relevant change (no caching).
- **`TeamRotationSummaryHeader.vue`** — a `position: sticky` card rendered above the main config card (as its direct sibling, not wrapped in an enclosing `<div>` — a sticky element can only stay "stuck" while scroll stays within its own *containing block*'s height, and a small wrapper div would become that containing block and run out of room almost immediately) showing team name, character avatars, action count, total damage/DPS, and a `TeamRotationDamageBar`. Uses an `IntersectionObserver` on a zero-height sentinel (with `root: null`, i.e. the viewport — the `/teams` route's real scroll position lives on `document.documentElement`/`window`, not `document.body`) to detect when it's "stuck" below the app's fixed nav, at which point it swaps to a condensed single-row layout (name, avatars, action count, damage, compact bar) via a "View Damages" button that opens the same drawer.
- **`TeamRotationDamageBar.vue`** — a pure-CSS horizontal stacked bar showing each character's share of total team damage (`compact` prop hides the per-character legend row); reused by both the summary header's expanded and stuck layouts. Renders nothing when there's no damage yet (e.g. no action has a valid attack key), since an all-empty bar has nothing meaningful to show.
- **`TeamRotationImportRotation.vue`** — a modal, opened per character slot, listing that character's own saved rotations (`characters[id].rotations`) and character-authored presets (`chosenChar.rotations` from `characters/<Name>/presets.ts`), each with "Append" (add after the slot's existing actions) and "Overwrite" (replace the slot's existing actions) buttons. Conversion to team actions — regenerating ids, assigning the target slot, and continuing the order sequence — is the pure `convertRotationActionsForSlot` in `calculator/teamRotation.ts`.
- **`TeamRotationActionEditor.vue`** — thin wrapper around the existing single-character `CalculatorRotationAction.vue` that adds a "which of the 3 teammates" slot selector. No Basic/Advanced mode concept (issue #401 — the toggle that used to gate this was removed): whenever a character is assigned to the action's slot, it injects an extra "Configure Buffs" toggle button (via `CalculatorRotationAction`'s `#extra-buttons` slot) and, once open, its panel (via the `#extra-panel` slot) — `TeamRotationAdvancedBuffs.vue`, plus a "Copy previous action settings" button (copies the immediately-preceding same-slot action's `advancedConfig`) shown inside that same panel. Feeds `TeamRotationAdvancedBuffs.vue` a `displayedAdvancedConfig` computed — `action.advancedConfig ?? buildAdvancedConfigSnapshot(characterDataForSlot[action.slot], definitionsForSlot[action.slot], "current")` — the same **display-only** fallback pattern `CalculatorRotationActionEditor.vue` already used, so an untouched action shows that slot's character's real current buff state instead of misleadingly-blank checkboxes; nothing is written just from opening the panel, only a real toggle persists a config. Using slots (rather than a separate sibling `<div>`) keeps this team-rotation-specific UI visually and structurally part of the same action row/card instead of a disconnected block underneath it.
- **`CalculatorRotationActionEditor.vue`** — the single-character rotation page's counterpart to `TeamRotationActionEditor.vue`, same wrapper-around-`CalculatorRotationAction.vue`-via-slots pattern, minus the slot selector (there's only one character). No Basic/Advanced mode concept here either — every action can just optionally carry an `advancedConfig`; the "Configure Buffs" button/`TeamRotationAdvancedBuffs.vue` panel is always available (issue #401 — replaced the old "Exclude team buffs"/"Exclude weapon buffs" checkboxes, which zeroed whole stat categories after the fact and had a bug where an `echoAttacks` action checking *either* one also silently dropped all echo contributions). Feeds `TeamRotationAdvancedBuffs.vue` the `modelValue` prop from `action.advancedConfig ?? buildAdvancedConfigSnapshot(characterBuildData, definitions, "current")` — the same display-only fallback described above. Forwards `toggleEdit()` to the wrapped `CalculatorRotationAction` via its own `defineExpose` (needed for `CalculatorRotation.vue`'s "auto-open a newly-added action for editing" behavior, which grabs a template ref by id). `CalculatorRotation.vue` owns the actual damage math split (see `calculator/characterRotation.ts`) and the `previousAction`/`rangeActions` (Duration control) computeds, scoped to that one rotation's own actions rather than a whole team's.
- **`CalculatorRotationAction.vue`** — the shared "one rotation action" row/card, used by both the Calculator page's own rotations and Team Rotations. Collapsed header is two lines: order/count/title on top; forte/damage-type pills, a buffs-count badge, a "Configure Stats" toggle (reveals the manual buff-modifier list — `CalculatorRotationActionBuff` rows + "Add Buff", plus a "Disabled" checkbox when `showDisabledOption`), an optional slotted extra button (both rotation types' "Configure Buffs"), and a Delete button on the second line. Clicking the row itself (anywhere not `@click.stop`-guarded) toggles a separate "choose attack, order, count" edit form — kept independent from the "Configure Stats" panel so each can be shown/hidden on its own. Exposes `#extra-buttons` and `#extra-panel` slots so a wrapper (`TeamRotationActionEditor.vue` / `CalculatorRotationActionEditor.vue`) can render its own per-action controls/panels inside this same card rather than as a disconnected sibling block. No longer owns any buff-exclusion state itself (issue #401) — that now lives entirely in the wrapper's `advancedConfig` handling.
- **`TeamRotationAdvancedBuffs.vue`** / **`TeamRotationAdvancedBuffRow.vue`** — the advanced per-action buff editor shared by both rotation types (despite the `TeamRotation*` name — kept as-is rather than renamed, to limit the blast radius of issue #401's changes). Lists every self buff/weapon passive/echo set passive/main echo buff/team buff/resonance chain available for that action's character (from `buildCharacterCalculationContext`'s `definitions` catalog) as an independently toggleable (+ stacks where applicable) checkbox row, writing to `action.advancedConfig`. Each row also has a "Duration" control — apply that buff's current on/off (+ stacks) state across a range of later actions, either "# actions" (a count) or "until action" (an `AppRichSelect` picker, inclusive) — so a buff doesn't need re-toggling action by action. This is a UI convenience only: it bulk-writes the same concrete override into each covered action's `advancedConfig` via the pure `applyBulkAdvancedConfigOverride` (`calculator/rotationAdvancedBuffs.ts`) — there's no persisted "span"/duration data structure, and the per-action calculation pipeline is unchanged. For Team Rotations the range is drawn from the *whole team's* actions across every character (`TeamRotationTeamEditor.vue`'s `orderedActionRangeList`), since a buff's duration is about the rotation's real timeline, not any one character's action count; for Character Rotations it's scoped to that one rotation's own actions (`CalculatorRotation.vue`'s `rangeActions`). (Writing the override into another character's action is a harmless no-op unless that character happens to share the same buff key.)
- **`TeamRotationDamages.vue`** — total damage + DPS summary, modeled on `CalculatorDamages.vue`'s rotation summary card and using the shared `calcRotationDps` helper; forwards `CalculatorDamage`'s `selected-attack` event up to the team editor's drawer to switch to the breakdown view. Owns a local Normal/Average/Crit toggle (seeded from the `settings` store's `chartDamageMetric` preference, default "average", same as `CalculatorDamageChart.vue`) passed as the `metric` prop into its `TeamRotationDamageChart.vue` pie chart.
- **`TeamRotationDamageChart.vue`** / **`TeamRotationCharacterTimelineChart.vue`** / **`TeamRotationCumulativeDamageChart.vue`** — the "per character" charts (pie, avg-damage-over-time line, cumulative stacked line); each takes an optional `metric: ChartDamageMetric` prop (`"normal" | "average" | "crit"`, default `"average"`, from `utils/chartPreferences.ts`) selecting which of `normalDamage`/`avgDamage`/`critDamage` to plot — the caller owns the toggle UI (`TeamRotationDamages.vue`'s own toggle, or `TeamRotationSummary.vue`'s single shared toggle governing all three at once), since these components stay presentational. `TeamRotationTimelineChart.vue` is the exception: it always plots all three as separate lines rather than reading `metric`, since it's the one chart meant to compare the metrics against each other rather than show one series per character.
- **`TeamRotationEnemySettings.vue`** — the team's shared enemy config panel (level/resist/type, tune strain stacks, and all elemental negative-status stacks), bound via `v-model` to `team.enemyConfig` (`TeamEnemyConfig` in `calculator/buildCharacterContext.ts`). Unlike `CalculatorEnemy.vue`'s equivalent sliders on the single-character Calculator page, every status slider here renders unconditionally — a team has up to 3 characters, so gating sliders on "does the active character need this status" (as `Calculator.vue` does per `basic.ts` flags) doesn't cleanly generalize; showing all of them is the simpler, deliberate choice.

## Where to look when changing behavior

- **Stats or damage wrong**: `calculator/stats.ts`, `calculator/calculator.ts`, `calculator/attacks.ts`, and the handlers in `Calculator.vue` that call `computeAllBuffsWithBreakdown` and `calcAllDamages`.
- **UI not updating**: Check that the relevant ref/reactive is updated in a handler and passed as a prop to the child; ensure the child uses that prop (or store) in template/computed.
- **New screen or step**: Add a new screen ref and sub-nav entry, add a handler that updates state and runs the same pipeline if it affects stats/damage, and pass the needed props into the new component.
